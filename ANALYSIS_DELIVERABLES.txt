KEY FINDINGS SUMMARY
================================================================================

CURRENT ARCHITECTURE:
✓ Queue-based async pattern (Submission → Event)
✓ Single submission_loop dispatcher
✓ One active task per session enforced
✓ Well-abstracted tool system (11 handlers)
✓ Event system with per-submission correlation
✓ Modular task types (SessionTask trait)
✓ Flexible LLM provider support

CRITICAL CONSTRAINTS:
✗ One active task per session (no parallel agents)
✗ Sequential submission processing
✗ Turn-level parallelism only (within a turn)
✗ Single cancellation token (broadcast-style)

MULTI-AGENT READINESS:
✓ SessionTask trait enables new task types
✓ ToolRouter abstraction is tool-agnostic
✓ ToolOrchestrator already modular
✓ ApprovalStore already keyable
✓ Event correlation ready for extension

PRESERVATION REQUIREMENTS:
✓ Event ordering guarantees
✓ Session isolation
✓ Approval system semantics
✓ Rollout persistence
✓ Cancellation guarantees

ARCHITECTURE HIGHLIGHTS
================================================================================

ENTRY POINT:
  Codex::spawn()
    └─ Creates single Codex + Session + submission_loop task
    └─ Opens submissions channel (tx_sub) and events channel (rx_event)

MAIN LOOP:
  submission_loop(session, config, rx_sub)
    └─ Sequential dispatcher for all operations
    └─ Handles 13+ operation types
    └─ Routes to appropriate handler

TASK EXECUTION:
  Session::spawn_task(turn_context, input, task)
    ├─ Aborts previous task (TurnAbortReason::Replaced)
    ├─ Spawns tokio task running task.run()
    ├─ Emits TaskComplete event on finish
    └─ Stores task in active_turn mutex

TURN PROCESSING:
  run_turn(session, turn_context, input, cancellation_token)
    ├─ Streams from LLM via ModelClient
    ├─ Routes tool calls via ToolRouter
    ├─ Processes items in order
    ├─ Retries on stream errors (max 3x)
    └─ Returns token usage + collected items

TOOL EXECUTION:
  ToolRouter::dispatch_tool_call()
    ├─ Routes to appropriate ToolHandler
    └─ ToolHandler::handle()
        └─ Invokes ToolOrchestrator for approval/sandbox
            ├─ Request approval (if needed)
            ├─ Select sandbox
            ├─ Execute
            └─ Retry without sandbox (if denied)

STATE MANAGEMENT:
  Session {
    conversation_id: UUID,
    state: Mutex<SessionState> {
      session_configuration,
      history: ContextManager,
      latest_rate_limits,
    },
    active_turn: Mutex<Option<ActiveTurn>> {
      tasks: IndexMap<sub_id, RunningTask>,
      turn_state: Mutex<TurnState> {
        pending_approvals: HashMap<sub_id, Sender<ReviewDecision>>,
        pending_input: Vec<ResponseInputItem>,
      },
    },
    services: SessionServices {
      mcp_connection_manager,
      unified_exec_manager,
      notifier,
      rollout: Mutex<RolloutRecorder>,
      auth_manager,
      otel_event_manager,
      tool_approvals: Mutex<ApprovalStore>,
    },
  }

MULTI-AGENT PHASES
================================================================================

PHASE 1: MINIMAL VIABLE (Low Risk, 2-3 weeks)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Add optional agent_id field to Op (backward compatible)
- Create AgentRegistry wrapper around Session
- Route submissions to agents in submission_loop
- Each agent gets dedicated task queue (Option<RunningTask>)
- Agents share session state (history, auth, services)
- No breaking changes to protocol or public API

Impact:
  Benefits:  Easy migration, low risk, backward compatible
  Effort:    2-3 weeks
  Risk:      Low-Medium
  Breaking:  None

PHASE 2: CONCURRENT EXECUTION (Medium Risk, 4-6 weeks)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Per-agent executor loops (tokio::spawn)
- Independent submission channels per agent
- Shared session state with proper synchronization
- Hierarchical event ID (agent_id, operation_id)
- Approval caching keyed by (agent_id, request)

Impact:
  Benefits:  True concurrency, cleaner separation
  Effort:    4-6 weeks
  Risk:      Medium
  Breaking:  Protocol changes (additive, extensible)

PHASE 3: ADVANCED FEATURES (Higher Risk, TBD)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Agent-to-agent communication (tool calls)
- Hierarchical agents (parent/child coordination)
- Dynamic agent creation (spawn on demand)
- Agent-specific policies (access control)
- Tool conflict coordination (distributed locks)

Impact:
  Benefits:  Advanced capabilities
  Effort:    TBD
  Risk:      High
  Breaking:  Significant protocol changes needed
